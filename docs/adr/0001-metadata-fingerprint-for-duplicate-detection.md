# Use header-metadata fingerprint, not content hash, for duplicate detection

Files are accessed over WiFi from a NAS as well as from directly-attached external drives, so hashing full file contents (some masters are hundreds of MB) would mean streaming every byte of every file across the network on top of the header read the scanner already does — a real cost, not just CPU. Instead, duplicate Files are recognized by a fingerprint of (`size`, `DATE-OBS`, `EXPTIME`, `OBJECT`, `INSTRUME`) — fields the scanner already extracts from the header for every file regardless, so detecting duplicates adds zero additional I/O. `DATE-OBS` is a per-exposure capture timestamp, so two Files sharing the full fingerprint are effectively guaranteed to be the same exposure.

**Considered and rejected**: full SHA-256 content hash — more rigorous, but too slow over a NAS mount for routine scans. Deferred idea: running the scanner directly on the NAS (via SSH/Docker) to avoid the network-transfer cost entirely, which would make content hashing viable — not pursued now because it requires a remote-execution setup and a plan for reconciling a DB written from two machines, which is a much larger undertaking than the fingerprint approach it would replace.
